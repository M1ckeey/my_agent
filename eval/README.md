# Research Agent 评测计划

本目录用于保存固定题集、评测脚本和评测说明。**8 道题目已获用户审核保留并完成首次试跑；预期子问题与参考说明仍待逐项校准，正式基线尚未建立。**首轮结果与局限见 [首轮评测记录](first-evaluation.md)。现有单元测试验证代码行为；这里规划的评测用于衡量真实研究任务的输出质量。运行轨迹的约定见 [Harness 文档](../docs/harness.md)。

固定题目的入选条件、首批覆盖范围和人工校准步骤见 [题集选题规则](dataset-selection.md)。审核过程见 [研究题目候选](dataset-candidates.md)；当前题目和审核状态分别见 [dataset.jsonl](dataset.jsonl)、[dataset-meta.json](dataset-meta.json)。

**下一轮按 [七项评测指标](metrics.md) 逐题和汇总报告**；其中无法同口径计算的项须写明 `pending_review`、`not_applicable` 或 `unavailable`，不得填 0 或借用首轮的代理指标。

## 目标与边界

- 首先回答：任务能否完成、预期子问题是否有材料、引用是否能追溯到材料、运行消耗是多少。
- 把「来源存在」「报告内容与 finding 文本相符」「论断得到事实支持」分开记录。当前 Validator 主要完成前两类机械检查，不能把 `citations[*].supported` 直接称为事实准确率。
- 使用当前的 `ResearchState`、`ResearchFinding`、`run_id` 和 `thread_id`；评测先作为图运行结果的消费方，不为评分改动主流程的路由。
- 第一阶段不依赖 RAG、向量数据库或额外 LLM 裁判。加入这些能力后再扩展相应指标。

## 阶段一：建立固定题集

1. 先选 5–10 个主题，覆盖事实梳理、方案对比和需要指出信息不足的题目；稳定后扩至约 20 题。时间敏感题须记录评测日期或明确时点。
2. 每题保存稳定 `id`、`topic`、`category`、`expected_subquestions` 和人工核对的 `reference_notes`。参考材料用于人工复核，不能要求系统必须引用某个固定网址。
3. 记录题集版本和标注日期。修改题目或预期答案时升级版本，不把不同版本的分数混作同一条趋势。

示意记录（字段和措辞在实现前可调整）：

```json
{"id":"q001","topic":"比较 PostgreSQL 与 SQLite 在本地研究工具中的适用场景","category":"方案对比","expected_subquestions":["部署和维护成本","并发写入与持久化需求"],"reference_notes":["人工核对官方文档中的能力边界"]}
```

## 阶段二：运行并保存原始产物

1. 逐题启动一次独立研究，使用新的 `thread_id`；固定本轮模型、提示词、预算和工具配置。真实 API 运行与使用假服务的自动化测试分开。
2. 每题结束即保存 `raw/<id>.json`：题目 ID、`run_id`、`thread_id`、状态、错误、报告、子问题、`raw_findings`、压缩后的 findings、引用校验结果、研究步数、token 用量及报告路径。失败和中断也要留记录。
3. 保存本轮 `manifest.json`：题集版本、代码修订、模型与配置、运行时间、成功／失败题数。若工作区有未提交改动，记录这一事实，避免把不同代码的结果误作同一基线。
4. 重跑时按题目 ID 检查原始产物；只跳过确认完整的题目。缺失或损坏的产物要重新运行，不静默当成零分。

这一步只负责采集，不产生质量结论。单题任务的 LangGraph checkpoint 用于研究中断恢复；`raw` 文件用于评测复算，两者职责不同。

## 阶段三：离线评分与人工复核

`score.py` 只读取已保存的 `raw` 与同版本题集，汇总为 `summary.json`。更改评分规则时可重算，不必再次调用研究 Agent。下一轮的七项指标、计算公式、缺失口径和入门条件以 [指标契约](metrics.md) 为准；逐题评分产物与人工复核记录仍需补齐。

评分失败应标为 `partial` 或 `failed` 并说明缺失指标；不能将「没有算出」写成 0 分。RAG 接入后再启用有 gold 检索目标的检索命中率，避免当前没有知识库却报告 RAG 指标。

## 阶段四：建立基线与比较改动

1. 首轮运行留存逐题结果、汇总和人工复核记录，作为基线；同时列出已知失败案例。
2. 改模型、提示词、压缩策略或 Critic 后，使用**同一题集和同一评分口径**重跑，逐题比较覆盖、引用、消耗及失败原因；配置不同处必须列明。
3. 网络检索和 LLM 输出会波动。分数改善先视为观察结果，不能仅凭一次运行宣称改动有效；优先复核变化最大的题目，必要时重复运行。

## 第一批实施任务与完成标准

1. 建立人工校准的 5–10 题 `dataset.jsonl`，并为题集校验写小型测试。
2. 实现运行器的逐题 `raw` 保存和断点跳过；用可注入的假 Planner／Researcher 验证产物结构，再单独运行真实题目。
3. 实现不依赖 LLM 的完成率、来源可追溯率与消耗统计；人工标注子问题覆盖和论断支持。
4. 生成首份逐题评分和汇总报告，明确写出有效题数、未计算项、人工样本及局限。完成后再决定是否加入 LLM 裁判和更大的题集。
