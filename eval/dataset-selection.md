# 固定研究题集的选题与校准规则

本文约束 `eval/dataset.jsonl` 第一版题集的选取、人工标注与版本维护。目标是用同一批问题比较研究流程的完成、材料覆盖、来源可追溯和消耗；题目本身不能根据某次模型输出临时调整。运行与评分口径见 [评测计划](README.md)。

## 从 DeepResearch 借鉴什么

参考同类项目 DeepResearch 的 `research_engine/eval/dataset.jsonl` 与 `docs/requirements/5-eval-and-metrics.md`：它混合真实问题和人工补齐的问题，标注难度、任务类型、预期子问题；草案经人工校准；把曾经成功的回归题与未按系统表现筛选的能力题分开报告，并保存题集版本和代码修订。这些是选题与归因方法，不要求复制其题目、比例或评分阈值。

本项目第一版只评估**一次独立研究**。当前可用材料来自网页、arXiv 和项目内文件，计算器可处理确定性计算；尚无 RAG 知识库、跨会话长期记忆、企业内部数据或多轮评测运行器。因此不要把这些未实现能力作为第一版的必答条件。DeepResearch 的「≥20 题、单轮／多轮／计算／学术四类全覆盖」也不直接套用：先用 5–10 题建立可信的小基线，再扩充。

## 入选条件

一题须同时满足以下条件：

1. **任务明确**：题目写清对象、比较范围和所需结论；独立拿出题目也能理解。不用「最近」「主流」「更好」等未定义词。若确需使用，给出时间点、对象集合和比较维度。
2. **与当前能力匹配**：可以通过现有网页、arXiv、项目文件或计算器获得足够材料，并可在默认研究预算内形成有意义的报告。不要要求登录、付费数据库、私有知识库、现场实验或尚未接入的工具。
3. **可以核对**：人工标注者能找到至少一类可访问的权威或原始材料，核对重要事实或发现材料不足。`reference_notes` 记录核对线索与边界，不指定 Agent 必须命中某个网址。
4. **有研究价值**：至少包含两个可以独立检索或分析的方面；纯心算、单一事实查询和只有一个固定答案的题目留给工具单测，不占研究题集名额。
5. **口径稳定**：优先选版本、历史区间或原理明确的问题。涉及价格、政策、产品功能等易变化信息时，题目必须写明「截至 YYYY-MM-DD」，标注时记录核对日期；重跑仍按原时点评分。
6. **不预设系统成功**：先按覆盖目标选题，再运行 Agent。不能因为模型答不出而删题、把预期子问题改成模型实际生成的子问题，或只留下过去表现好的题。

「信息不足」题也应有清楚的可核对边界：例如公开材料只能支持定性比较，不能支持指定条件下的精确性能排名。人工标注要写出哪些部分可答、哪些部分应明确保留判断；不能用一个完全不可检索的问题测试 Agent 是否放弃。

## 第一批题目如何组合

首批建议 **8 题**，允许在 5–10 题范围内调整。每题指定一个主要类别，另用标签记录交叉特征；类别只是覆盖检查，不是评分权重。

| 主要类别 | 建议数量 | 主要检查点 |
| --- | ---: | --- |
| 事实梳理 | 2 | 能否拆出关键方面、找到可追溯材料 |
| 方案对比 | 2 | 是否按共同维度比较，并说明适用条件 |
| 学术证据 | 2 | 是否区分论文结论、实验条件和推断 |
| 定量估算 | 1 | 是否列出假设、公式和不可由资料确定的变量 |
| 信息不足 | 1 | 是否保留可回答部分，并明确证据缺口 |

难度应有易、中、难梯度，以中等难度为主；不要让全部题目集中于同一个技术主题或同一种网站。题目来源是另一维度：若有合适的真实任务记录，首批至少选 2 道去标识化的自然提问，分别归入上表的内容类别；不能只选过去成功的样例。若专门保留「曾经答对」的回归锚点，应单列 `bucket=regression`，与未按历史表现筛选的 `bucket=capability` 分开统计；第一批若没有可靠历史记录，就全部标为 `capability`，不虚构锚点。

难度标签按**预期研究工作量**预先判断，不按 Agent 首轮得分倒推：`易` 表示少量权威资料即可覆盖主要方面、结论稳定；`中` 表示需要跨来源或跨维度比较、计算并解释边界；`难` 表示需要核对多篇论文的任务、模型、基线或处理冲突证据。它是粗粒度标签，不保证各题耗时或实际成功率完全一致。

## 人工校准步骤

1. **先写题目，再写预期**：为每题确定稳定 `id`、原文 `topic`、主要类别、难度和选题来源。不要看本轮 Agent 答案后再决定预期。
2. **独立拆分**：人工写 2–4 条 `expected_subquestions`，每条聚焦一个可检查的方面，避免重复、空泛或把结论写进问题。它们是覆盖参照，不要求 Planner 使用完全相同的字词或数量。
3. **核对可回答性**：用可访问资料检查主题、时间范围及预期子问题是否合理；在 `reference_notes` 记录来源类型、关键事实与可能缺口。允许用模型生成草案，但须人工逐条删改，并记录校准状态。
4. **审查泄漏与偏差**：题目不能包含正确答案、预期引用清单或隐含的固定来源；不得因本项目当前提示词偏好而刻意改写为容易命中的措辞。
5. **冻结后运行**：保存题集版本、标注日期；评测产物同时记录题集版本、代码修订和运行配置。修改题目、预期子问题或评分规则时升级相应版本，旧结果保留，不与新版直接合并为一条趋势。

第一版每题至少保留 `id`、`topic`、`category`、`expected_subquestions`、`reference_notes`，与 [评测计划](README.md) 一致。建议另记 `difficulty`、`selection_origin`（真实问题／人工编写）、`bucket`、`as_of`（如适用）和 `annotation_status`；这些扩展字段在建立 `dataset.jsonl` 与校验器时一并定型。题集版本与标注日期可放在单独的元数据文件，不把元数据行当作研究题目。

## 常见拒收或改写情形

| 原题问题 | 处理方式 |
| --- | --- |
| 「2026 年最好的 Agent 框架是什么？」 | 指定使用场景、候选框架、比较维度和截至日期；否则拒收。 |
| 「A 比 B 快多少？」但没有共同硬件、负载或公开基准 | 改成比较性能影响因素和可核对的测试条件；不能预设精确倍数。 |
| 「用公司内部文档分析……」 | 当前没有私有知识库，留到 RAG／MCP 能力接入后的独立题集。 |
| 「123 × 456 等于多少？」 | 放进计算器测试，不作为研究质量题。 |
| 同一题要求现价、最新法规和未来预测 | 缩小范围并固定时点；预测与可核对事实分开。 |

## 入库前检查

- [ ] 题目无需上下文也可理解，范围和时点明确。
- [ ] 当前工具能访问所需材料，且没有隐藏的登录或私有数据依赖。
- [ ] 预期子问题由人工校准，彼此不重复，也不从 Agent 输出倒推。
- [ ] `reference_notes` 足以支持人工复核，并注明预期的信息缺口。
- [ ] 首批题目覆盖不同任务类别和难度，真实题未按历史成功率筛选。
- [ ] 题集版本、标注日期和选题来源可追溯；冻结后不就地改写旧基线。
